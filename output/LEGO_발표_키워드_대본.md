# LEGO 리뉴얼 — 10분 발표 키워드 대본

작성 기준: 2026-10-23

- 형식 참고: [Stanley 팀프로젝트(1) 발표 키워드 대본](https://app.notion.com/p/3bbbed83b4ed81cb9dc2c77901d9be9b)
- 슬라이드 기준: 첨부한 LEGO 최종 발표 PDF의 11장. 아래 01~11은 발표 순서이며, 사용성 점검(PDF 10번째 장) 다음에 실제 페이지 구현·시연(PDF 9번째 장)을 배치했다. 실제 구현·시연을 발표 본문의 마지막에 진행하고 마무리 인사로 끝낸다. 원본 PDF의 장 순서는 변경하지 않았다.
- 구현 기준: 로컬 프로젝트의 index.html, shop.html, gift.html과 각 CSS·JavaScript 파일을 대조했다. 브라우저에서 모든 기능의 실행 검증을 마쳤다는 뜻은 아니다.
- 이 문서는 새로 작성한 발표 대본이다. 프로젝트 코드와 원본 발표자료는 수정하지 않았다.

## 발표 원칙

> 문장을 전부 외우기보다 **키워드 → 설명 순서 → 한 문장 앵커**를 기억한다.

> 각 장에서는 **무엇을 구성했는가 → 왜 그렇게 구성했는가 → 화면에서 어떻게 이어지는가** 순서로 설명한다.

> 아래 ‘말할 내용’은 연습용 문장이다. 실제 발표에서는 표현이 조금 달라도 핵심과 순서만 유지하면 된다.

> ‘한 문장 앵커’는 말이 막힐 때 돌아올 문장이다. 말할 내용 뒤에 매번 추가로 읽을 필요는 없다.

## 발표 전체 핵심 메시지

**취향을 발견하고 → 상품을 탐색하고 → 선물을 선택하는 레고 웹 경험**

이 문장은 현재 구현을 설명하기 위한 발표용 핵심 메시지다. 별도로 확인하지 않은 시장 조사나 기존 사이트의 문제점을 사실처럼 덧붙이지 않는다.

| 콘텐츠 키워드 | 연결할 페이지와 설명 |
| --- | --- |
| 취향 | Main — 신제품, 인기 시리즈, 홈 스타일링을 통해 관심 있는 콘텐츠 발견 |
| 탐색 | Shop — 카테고리를 선택하고 해당 상품 목록 확인 |
| 선물 | Gift — 인기 상품과 선물 대상, 나를 위한 선물 콘텐츠 소개 |

구현을 설명할 때 반복할 키워드는 **공통 관리 · 디자인 일관성 · 상호작용 · 반응형**이다.

## 03. 프로젝트 파일 구조 설계

### 기억할 키워드

`HTML / CSS / JavaScript / images` · `공통 파일` · `페이지별 파일` · `유지보수`

### 설명할 순서

1. HTML은 index.html, shop.html, gift.html로 페이지 구분.
2. common.css는 공통 디자인, common.js는 공통 메뉴 동작 관리.
3. 각 페이지의 디자인과 동작은 이름이 같은 CSS·JS 파일에 작성.
4. 이미지 파일은 images 폴더에서 관리.

### 말할 내용

“파일은 화면 구조를 담당하는 HTML, 디자인을 담당하는 CSS, 동작을 담당하는 JavaScript, 그리고 이미지로 나눴습니다.

또 여러 페이지에서 함께 사용하는 부분과 각 페이지에서만 사용하는 부분을 구분했습니다. 예를 들어 헤더와 푸터의 스타일은 common.css에서, 메뉴를 펼치는 동작은 common.js에서 관리합니다.

페이지마다 달라지는 부분은 별도 파일에 작성해서, 수정할 때 어느 파일을 확인해야 하는지 쉽게 찾을 수 있도록 했습니다.”

### 한 문장 앵커

**“공통으로 사용하는 코드와 페이지마다 달라지는 코드를 나눠 관리했습니다.”**

### 쉽게 풀어 말하기

유지보수 = 완성한 뒤에도 필요한 부분을 찾고 고치기 쉽게 관리하는 것.

주의: 공통 CSS·JS를 연결한 구조다. 헤더와 푸터 HTML 자체를 한 파일에서 자동으로 불러오는 구조라고 설명하지 않는다.

## 05. 파일 구조 — SHOP

### 기억할 키워드

`shop.html` · `상품 데이터` · `카테고리` · `목록 전환`

### 말할 내용

“상품 페이지는 shop.html, shop.css, shop.js로 구성했습니다.

이 페이지에서는 상품명, 가격, 이미지, 카테고리 같은 정보를 JavaScript의 상품 목록에 모아 두었습니다. 카테고리를 클릭하면 그 분류에 맞는 상품을 골라 화면에 다시 보여줍니다.

상품 정보를 관리하는 부분과 화면에 보여주는 부분을 연결해, 원하는 제품군을 선택하며 탐색할 수 있도록 구현했습니다.”

### 한 문장 앵커

**“상품 정보를 기준으로 카테고리에 맞는 목록을 보여주는 방식입니다.”**

### 질문을 받으면 설명할 내용

- 배열 = 상품 여러 개를 순서대로 담아 놓은 목록. 코드에서는 products.
- filter() = 조건에 맞는 상품만 골라 새 목록을 만드는 기능.
- displayProducts() = 전달받은 상품 목록을 화면의 카드로 보여주는 함수.
- 상품 정보는 현재 JavaScript 파일 안에 있다. 서버나 데이터베이스에서 받아오는 구조라고 말하지 않는다.

## 07. UI 리소스와 디자인 시스템 — 폰트·컬러

### 기억할 키워드

`Noto Sans KR` · `IBM Plex Sans` · `다크 배경` · `레드 / 라임` · `디자인 일관성`

### 설명할 순서

1. 두 폰트를 사용해 텍스트 구성.
2. 어두운 배경과 밝은 글자로 화면의 기본 분위기 통일.
3. 레드는 강조할 단어, 라임은 주요 버튼과 강조 요소에 활용.
4. 공통 색상·글자 크기 기준을 CSS 변수로 관리.

### 말할 내용

“디자인 기준으로는 Noto Sans KR과 IBM Plex Sans를 사용했습니다. 제목과 설명, 버튼의 글자 크기와 굵기에 차이를 두어 어떤 정보를 먼저 읽어야 하는지 구분했습니다.

전체 화면은 어두운 배경과 밝은 글자를 중심으로 구성했고, 빨간색은 중요한 단어를 강조하는 데, 라임색은 주요 버튼과 강조 요소에 사용했습니다.

이 기준들은 공통 CSS에 변수로 정리했습니다. 같은 색상이나 글자 크기를 여러 페이지에서 함께 사용해 디자인의 일관성을 유지하도록 했습니다.”

### 한 문장 앵커

**“폰트와 색상 기준을 공통으로 관리해 세 페이지가 하나의 사이트처럼 보이도록 했습니다.”**

### 발표자 참고

- CSS 변수 = 자주 쓰는 디자인 값에 이름을 붙여 다시 사용하는 것. 예: --pointRed.
- 슬라이드의 숫자를 모두 읽을 필요는 없다. 색상의 역할과 통일된 기준을 설명한다.
- PDF의 라임색 #d5f827과 현재 공통 CSS의 --pointLime 값 #D7FA24는 다르다. PDF의 흰색·제목 굵기·고정 글자 크기도 현재 코드와 완전히 같지는 않다. ‘가이드의 모든 수치를 그대로 적용했다’고 말하지 않는다.
- 현재 글자 크기 일부는 clamp()로 화면 너비에 따라 달라진다.

## 09. 사용성 점검 — 기능 및 UI/UX

### 기억할 키워드

`구조` · `동작` · `반응형` · `구현 범위`

### 말할 내용

“사용성 점검 항목은 크게 화면 구조, 기능 동작, 반응형으로 정리했습니다.

화면 구조에서는 주요 영역과 제목, 콘텐츠가 구분되는지, 이미지와 텍스트가 화면 밖으로 벗어나지 않는지를 살펴보는 기준을 세웠습니다.

기능에서는 메뉴 펼침, 배너 전환, 상품 분류처럼 실제 구현한 동작을 중심으로 점검할 수 있도록 했습니다. 반응형에서는 PC와 태블릿, 모바일 너비에서 메뉴와 콘텐츠 배치가 어떻게 바뀌는지를 확인하는 항목으로 정리했습니다.

현재 구현 범위는 콘텐츠 화면과 주요 화면 동작입니다. 구매나 계정 연동, 영상 재생처럼 추가 연결이 필요한 부분은 남아 있습니다. 따라서 모든 서비스 기능이 완성됐다고 설명하기보다는, 구현한 기능과 앞으로 연결할 기능을 구분해서 말씀드리겠습니다.”

### 한 문장 앵커

**“화면 구조와 주요 동작, 반응형을 점검 기준으로 삼고, 현재 구현 범위도 함께 구분했습니다.”**

### 발표자 참고

- PDF에는 10개 항목에 모두 체크 표시가 있다. 하지만 체크 표시만으로 실제 테스트를 모두 통과했다고 판단할 수는 없다.
- 현재 코드에는 href="#" 링크와 연결되지 않은 영상 버튼이 있다. ‘모든 메뉴와 링크가 정상 작동한다’는 설명은 피한다.
- 다른 사용자를 대상으로 한 테스트 기록이나 HTML 검사 결과는 이번에 확인되지 않았다. 사용자 검증 완료, 문법 오류 0건 같은 결과를 만들어 넣지 않는다.
- 실제로 수행한 테스트와 수정 사례를 보스가 추가로 알려주면, 그 근거에 맞춰 이 장을 구체적인 결과 설명으로 바꿀 수 있다.

다음은 특별한 선물 영역입니다. 기념일별 이미지를 통해 선물 콘텐츠를 소개하고 선물 페이지로 연결했습니다.

**“메인에서는 상품과 시리즈, 선물과 공간 연출을 연결해 다양한 취향을 발견하도록 구성했습니다.”**

- 뉴스 상세, 구매, 멤버십 등 연결이 없는 버튼을 실제 서비스 기능처럼 소개하지 않는다.

### 10-2. SHOP — 약 1분 20초

#### 기억할 키워드

2. Vehicle 클릭 → 해당 상품과 하위 분류 확인.
3. F1 클릭 → 더 좁은 상품 분류 확인.

### 10-3. GIFT — 약 1분 5초

#### 기억할 키워드

`인기 상품` → `선물 대상` → `나를 위한 선물` → `브랜드 이야기`

#### 화면을 보면서 말할 순서

1. 첫 화면의 ‘선물찾기’ 클릭 → 대상별 선물 영역으로 이동.
2. 인기 상품은 위치를 짚고, 이전·다음 버튼으로 한 번 넘기기.
3. 가족·나·연인·친구/동료의 대상별 콘텐츠 소개.
4. 나를 위한 선물 목록에 마우스를 올려 오른쪽 번호의 확대 효과 소개.
5. 브랜드 이야기 영역은 소개 화면으로 설명.

#### 말할 내용

“선물 페이지는 누구에게 어떤 선물을 줄지 생각하며 살펴보는 흐름입니다.

첫 화면의 선물찾기 버튼을 누르면 대상별 선물 영역으로 이동합니다. 인기 상품 영역에서는 이전·다음 버튼으로 상품을 넘겨볼 수 있습니다.

선물 대상은 가족, 나, 연인, 친구나 동료로 나눠 보여줬습니다. 이 카드들은 레고 공식 사이트의 관련 선물 페이지로 연결했습니다.

아래에는 나를 위한 선물도 소개했습니다. 상품 목록에 마우스를 올리면 오른쪽의 해당 번호가 커지도록 해 상품과 이미지를 연결했습니다.

마지막에는 레고를 좋아하는 사람들의 이야기를 소개하는 화면을 배치했습니다.”

#### 한 문장 앵커

**“선물 대상과 나의 취향을 기준으로 선물 콘텐츠를 살펴보도록 구성했습니다.”**

#### 시연 주의

- ‘대상 선택에 따라 사이트 안의 상품 목록이 자동 추천된다’고 말하지 않는다. 대상 카드는 외부 공식 페이지로 이동하는 링크다.
- 링크는 구현되어 있지만, 카드 이름과 외부 페이지의 세부 주제가 모두 일치한다고 단정하지 않는다. 예를 들어 ‘나’ 카드는 현재 wedding-gifts로 연결된다. 발표에서는 외부 탭 이동을 생략하고 연결 방식만 설명해도 된다.
- 하트는 현재 화면에서 이미지가 바뀌는 기능이다. 계정에 저장되거나 새로고침 후 유지되는 찜 목록은 아니다.
- 브랜드 이야기 영역에는 재생 기능이 연결되지 않았다. ‘영상이 재생됩니다’라고 설명하거나 재생 버튼을 시연하지 않는다.
- 실제 순서대로 스크롤한다면 인기 상품 → 선물 대상 → 나를 위한 선물 → 이야기 순서로 설명해도 된다. 이 경우 첫 화면의 선물찾기 버튼은 위치만 짚고 넘어간다.
